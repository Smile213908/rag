## 路线总览

```text
M0 技术底座(已完成)          M1 产品化 MVP           M2 体验与运营           M3 能力跃迁
传统 RAG 链路跑通     ──▶    可用的 Web 产品   ──▶    多轮+运营+权限   ──▶    GraphRAG 复杂推理
(CLI 原型)                  (小范围试用)             (扩大推广)              (能力分层)
   ✅                          2~3 周                   2~3 周                  视价值验证
```

> 核心策略:**先把传统 RAG 做成好用的产品,再按真实瓶颈决定要不要上 GraphRAG**——避免为用技术而用技术。

---

## M0 技术底座 ✅(已完成)

**目标**:验证传统 RAG 链路在真实数据上可行。

**已交付**
- PDF 解析(PyMuPDF)+ 页眉页脚清洗;
- 结构递归分块(256~512 字,overlap);
- bge-m3 稠密向量(Chroma 容器持久化)+ BM25 混合检索;
- bge-reranker 精排;Kimi(k3)生成带引用答案;
- CLI 原型(`pipeline.py`)可问答。

**验证结论**:跨文档分流、多片段综合、库外拒答、引用溯源均正常。

**遗留(产品化必须补)**
- 无 Web 界面(仅 CLI);无拒答阈值显式判断;无多轮上下文;无知识库管理;无反馈/日志。

## M1 产品化 MVP(2~3 周)— 做出"能用"的产品

**目标**:员工能通过 Web 界面提问,HR 能上传文档,系统可信可溯源。

> **进度(2026-07-30):M1 八个工作项全部落地 ✅**,验收实测四项标准三过一挂(延迟 P95 71.5s 超标,挂账 M2 P0)——结论:**有条件通过**,详见 [[05-M1验收报告]]。

| 工作项 | 内容 | 产出 | 依赖 |
|--------|------|------|------|
| 后端服务化 | FastAPI 封装引擎层为 API | `/chat/ask`、`/documents/*` ✅(2026-07-30) | 现有代码 |
| 拒答机制 | reranker 分数阈值分流 | 拒答话术 + 阈值可配 ✅(0.7,评估集标定) | 需小评估集调阈值 |
| 引用溯源 | 来源映射 + 原文展开 | 前端可点 `[来源N]` ✅ | 检索已返回元数据 |
| 流式输出 | SSE | TTFT 优化 ✅ | LLM 支持流式 |
| 文档管理 | 上传→解析→索引→列表→删除 | 知识库管理页 ✅(`/documents` 五接口) | 引擎层索引能力 |
| Web 前端 | 问答界面 + 知识库页 | React + SSE ✅(`frontend/`,2026-07-30) | API 就绪 |
| 反馈闭环 | 👍👎 + bad case 入库 | 反馈接口 + 存储 ✅(`logs/bad_cases.jsonl`) | 业务库 |
| 评估集 v1 | 50 条标注问答建基线 | 离线评估脚本 ✅(Hit@5=100%) | 业务理解 |

**M1 验收标准**(对齐 PRD §2.2)
- 事实型问题 Top-1 正确率 ≥ 90%(评估集);
- 库外问题拒答率 ≥ 95%,无误编;
- 答案 100% 带可展开来源;
- P95 延迟 ≤ 8s(CPU)。

**M1 风险**
- 前端工作量可能被低估 → 可用现成聊天组件(如 Chatbot UI)二开;
- 拒答阈值难调 → 先用评估集标定,宁严勿松。

## M2 体验与运营(2~3 周)— 做出"好用 + 可运营"

**目标**:提升体验(多轮、更快)、建立运营闭环(知道哪里答得不好)。

| 工作项 | 内容 | 价值 |
|--------|------|------|
| **模型路由(P0,验收挂账)** | 简单问题走快模型(非推理模型)、CRAG 提速(快模型 + few-shot) | 延迟 P95 71.5→53.0s,F06 类误杀清零 ✅(2026-07-30) |
| 多轮对话 | 指代消解改写 + 会话上下文 | 对话式连续追问 ✅(2026-07-30,三轮实测) |
| 运营看板 | 命中率/拒答率/延迟/token + 高频问题 | 发现制度盲区 ✅(2026-07-30,含 bad case 闭环界面) |
| bad case 闭环 | 👎聚类归因→修复→回归 | 质量持续提升 |
| 权限控制 | 登录 + 按部门/角色过滤文档 | 数据隔离 |
| 性能优化 | 缓存、reranker 候选收敛、并行 | 延迟 ↓ |
| 增量索引 | 文档变更只重处理该文档 | 维护成本 ↓ |
| 评估集扩充 | 100 条 + 覆盖多跳/对抗 | 更可靠的回归 |

**M2 验收标准**
- 👍率 ≥ 85%;自助解决占比(北极星)有正向趋势;
- bad case 周处理闭环运转;
- 权限过滤生效(越权文档不可见)。

## M3 能力跃迁(视 M1/M2 真实瓶颈)— GraphRAG

**触发条件**(满足其一才投入,避免过度工程):
- 评估/运营数据显示**多跳推理、跨文档综合、全库总结**类问题占比高且当前答不好;
- 知识库规模增长,结构关系价值凸显。

**工作项**(详见大脑笔记 [[GraphRAG 工程落地]])
- 引入 LightRAG(轻量、增量友好)在现有 bge/Chroma/云端 LLM 底座上叠加实体关系图;
- 或用 Kimi 抽实体自建轻量图谱(NetworkX)做技术验证;
- **查询路由分层**:简单事实 → 传统 RAG;多跳/总结 → GraphRAG Local/Global;
- 评估对比:GraphRAG 在目标问题类型上 vs 传统 RAG + 子问题分解。

**M3 原则**:GraphRAG 不替代传统 RAG,而是**分层协作**;索引成本用"抽取小模型、生成大模型"压制。

## 技术债与升级路径(贯穿各期)

| 项 | 现状 | 升级路径 | 时机 |
|----|------|----------|------|
| 算力 | 全 CPU | reranker/编码上 GPU,延迟 ≤3s | M2 或并发上来后 |
| 向量库 | Chroma 单机 | Milvus/Qdrant 集群 | 块数达十万级 |
| 关键词索引 | rank_bm25 内存 | Elasticsearch | 文档规模大/需复杂过滤 |
| 业务库 | SQLite | Postgres | M2 |
| 解析 | PyMuPDF(纯文字) | MinerU/版面分析 + OCR | 接入复杂版面/扫描件时 |
| 模型 | bge-m3/reranker-base | 按需换更大/SOTA 模型 | 评估驱动 |
