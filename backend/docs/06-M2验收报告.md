## 2. 延迟不达标的根因(分解实测)

对 F15(快模型样本)逐阶段计时:

| 阶段 | 耗时 | 说明 |
|------|------|------|
| 检索+精排 | 6.4s | CPU:问题编码 + bge-reranker 对 20 候选打分(RECALL_TOP_N 已从 50 收敛 20) |
| CRAG 质检 | 4.8s | LLM 判定(快模型);决策:全分带保留,不可跳过 |
| LLM 首 chunk | 4.0s | kimi-for-coding 为思考型模型,首内容 chunk 前有隐藏推理 |
| 生成余量 | ~0.7s | 183 字答案流式跟出很快 |

- **M1 验收报告「流式 TTFT 2~3s」的假设实测证伪**:该值从未实测,思考型模型(k3/kimi-for-coding)的首 chunk 必然等待推理完成,TTFT≈端到端。
- 极端样本:MT1/MT2(合住/交通费)触发长推理,端到端 59~95s(含空输出重试,见 §3)。
- **CPU 底座无解**:检索 6.4s 单项已超 TTFT 3s 目标;PRD「检索+重排 ≤ 3s」NFR 同样未达(6.4s)。

## 3. 验收抓到的 bug:P1 封顶致空答案(已修复并复测)

- **现象**:批 2 中 MT1/MT2 回答为空(tokens 1749/1689 但 0 字),且空答案被写入缓存(毒化)。
- **根因**:P1 快模型封顶 `FAST_MAX_TOKENS=512` 的假设错误——kimi-for-coding **也是思考型模型**,隐藏推理烧 completion 预算,512 烧光后内容为空;2048 仍有极端样本烧光(MT2 实测 2043 completion token 全为推理)。
- **修复**(`54cb3f2` 之后,本次验收提交):
  1. `generator.py`:空输出自动去封顶重试一次(流式/非流式两路;空输出时未 yield 任何内容,重试安全)——**宁慢不空**;
  2. `FAST_MAX_TOKENS` 默认 512 → 2048(减少触发重试的概率);
  3. `anscache.put`:空答案不写入(防缓存毒化,已单测)。
- **复测**:MT1/MT2 重跑均正答(275/1009 字),缓存库清空后未再出现空记录。
- **代价**:触发重试的样本端到端翻倍(59~95s),已计入延迟数据。

## 4. 挂账与口径建议(待拍板)

延迟现状(CPU 底座):缓存命中 1ms;首问 P50 36.7s / P95 86.1s;TTFT 与端到端近似(思考型特性)。建议口径:

| 指标 | 建议值 | 依据 |
|------|--------|------|
| 缓存命中响应 | ≤ 100ms | P0 已兑现(1ms 实测) |
| 简单问题端到端 P95 | ≤ 90s(CPU 底座)/ ≤ 30s(GPU 升级后) | 本次 P95=86.1s;GPU 主要压缩检索 6.4s 与推理 |
| TTFT | 不设硬指标,改监控项 | 思考型模型首 chunk 前推理不可流式,TTFT≈端到端;体感优化靠 meta 帧(来源先行展示,实测 ~11s 到达) |
| 空输出重试率 | 监控项 | asks.jsonl 可统计;重试样本延迟翻倍 |
