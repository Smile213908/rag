## 1. 架构总览

### 1.1 设计原则

1. **检索与生成解耦**:检索层(bge 本地)与生成层(云端 LLM)通过接口隔离,LLM 可替换;
2. **数据不出内网**:bge 模型、文档、向量库全部本地化,仅脱敏查询片段送云端;
3. **索引持久化**:向量落盘 Chroma,重启不重算(CPU 上编码成本高);
4. **评估驱动**:所有检索/生成参数改动须经评估集回归(见 PRD §6.3);
5. **渐进演进**:先传统 RAG 产品化,再平滑叠加 GraphRAG 图结构层。

```text
┌─────────────────────────────────────────────────────────────┐

│  服务层  API 网关(认证/限流/日志)                             │
│          ├─ 问答服务(查询理解→检索→重排→生成→溯源)            │
│          ├─ 知识库服务(文档上传/解析/索引/删除)               │
│          └─ 运营服务(日志/反馈/统计/bad case)                 │
├─────────────────────────────────────────────────────────────┤
│  引擎层  RAG 核心(当前 pipeline.py 的服务化)                 │
│          ├─ 查询理解(改写/指代消解)                          │
│          ├─ 混合检索(bge-m3 稠密 + BM25 稀疏)                │
│          ├─ 重排序(bge-reranker CrossEncoder)                │

├─────────────────────────────────────────────────────────────┤
```

## 2. 核心数据流

### 2.1 在线问答流(读路径)

```text
用户问题
  │ ① 查询理解(可选:多轮指代消解 / Multi-Query 改写)
  ▼
② 混合检索 ── 稠密:bge-m3 编码 → Chroma 余弦检索 Top-N
   │         ── 稀疏:BM25 关键词匹配
   │         └─ 加权 RRF 融合(DENSE_WEIGHT=0.7)+ 元数据权限过滤
   ▼
③ 重排序:bge-reranker 对 Top-N 成对打分,取 Top-K(默认 5)
   ▼
④ 拒答判断:reranker 最高分 < 阈值 → 返回拒答,记录日志
   │ (≥ 阈值继续)
   ▼
⑤ 生成:Top-K 片段 + 系统约束 prompt → 云端 LLM(SSE 流式)
   ▼
⑥ 组装:答案 + 引用溯源(文档/片段/分数)→ 返回前端
```

### 2.2 离线索引流(写路径)

```text
文档上传(PDF/Word/MD/TXT)
  │ ① 解析:PyMuPDF 提取 + 清洗页眉页脚
  ▼
② 分块:结构递归切分(标题>段落>句子),256~512 字,overlap 10~15%
   ▼
③ 向量化:bge-m3 编码稠密向量(CPU 批量)
   ▼
④ 入库:Chroma(向量+原文+元数据,确定性 ID doc#chunk_N)+ 重建 BM25
   ▼
⑤ 状态回写:文档标记"已完成",块数/时间记录
```

## 3. 模块设计

### 3.1 引擎层(核心,当前已实现)

| 模块 | 职责 | 当前实现 | 产品化改动 |
|------|------|----------|------------|
| 分块器 | 解析+清洗+结构分块 | `engine/chunking.py` | 增加 Word/HTML 解析;OCR(二期) |
| 检索器 | 混合检索+Chroma 交互 | `engine/retriever.py` | 加权限过滤、并发控制、缓存 |
| 重排器 | CrossEncoder 精排 | `engine/reranker.py` | 批量优化、置信度输出 |
| 拒答器 | 分数阈值+CRAG 质检两层+拒答日志 | `engine/refuser.py`+`engine/checker.py` | v1 阈值已标定 0.7;CRAG 二值质检已挡域邻近题;三档(模糊→精炼)留 v2 |
| 生成器 | LLM 调用+prompt 组装 | `engine/generator.py` | 加流式 SSE、多轮上下文、引用映射 |
| 查询理解 | 改写/指代消解 | (待加) | **新增**:多轮改写、Multi-Query(可选) |

> 编排与服务层:`engine/pipeline.py`(CLI/引擎内核)、`engine/kb.py`(知识库文档级管理)、`api/server.py`(FastAPI,见 docs/03);共享路径常量集中在 `engine/paths.py`。

### 3.2 服务层(产品化新增)

- **API 网关**:认证(JWT)、限流、请求日志、统一错误码;
- **问答服务**:编排引擎层完成问答,管理会话上下文;
- **知识库服务**:文档 CRUD、索引进度、删除级联;
- **运营服务**:提问日志、反馈收集、高频问题聚合、bad case 池。

### 3.3 数据层

| 存储 | 内容 | 选型 | 说明 |
|------|------|------|------|
| 向量库 | 稠密向量+原文+元数据 | Chroma(docker) | 已有;规模化可换 Milvus/Qdrant |
| 关键词索引 | BM25 倒排 | rank_bm25 | 内存;文档增多后需持久化或换 ES |
| 业务库 | 用户/文档/日志/反馈/权限/**模型注册表** | SQLite→Postgres | 一期 SQLite 轻量起步 |
| 文件存储 | 原始文档 | 本地磁盘/MinIO | 一期本地即可 |
| 模型仓库 | 嵌入/重排模型文件 | 本地 `../model/` | 可注册多模型,当前生效由注册表指针决定 |

### 3.4 模型管理层(Model Registry)—— 新增核心模块

> 把模型从「代码写死」抽象为「可注册、可切换的资产」,支撑 F7 模型管理。

**核心概念**
- **模型记录(ModelRecord)**:一次注册的模型,含元数据;
- **当前生效指针(active pointer)**:全局唯二的「当前嵌入模型」和「当前重排模型」;
- **加载器(loader)**:按模型类型选择 `SentenceTransformer`(嵌入)/ `CrossEncoder`(重排)。

**模型记录结构**
```
ModelRecord {
  model_id:      唯一标识(如 bge-m3,或用户命名)
  type:          embedding | reranker
  version:       版本/标签
  path:          模型仓库中的物理路径
  source:        builtin(内置) | uploaded(用户上传) | modelscope
  status:        validating | ready | active | failed | disabled
  metadata:      { 向量维度, 最大序列长度, 模型结构, 文件大小 }
  uploaded_by / uploaded_at
}
```

**上传解析流程**
```text
上传 zip/tar.gz
  │ ① 解包到临时目录
  ▼
② 校验必需文件:config.json + 权重(pytorch_model.bin/model.safetensors)
   + 分词器(tokenizer.json);嵌入模型另需 modules.json/sentence_bert_config
   │ 缺文件 → status=failed,返回缺失清单
   ▼
③ 试加载(dry-run):用对应 loader 加载并跑一次前向(嵌入出维度/重排出分数)
   │ 加载失败 → status=failed,返回报错
   ▼
④ 提取元数据(向量维度、最大序列长度、结构)写入 ModelRecord,status=ready
   ▼
⑤ 移动到模型仓库正式路径,注册表落库
```

**切换与一致性保护**
- 切换**重排模型**:只影响打分,直接热加载即可,无数据迁移;
- 切换**嵌入模型**:**向量空间改变,全部旧向量失效** → 平台强制提示,确认后:
  1. active 指针切到新嵌入模型;
  2. 清空 Chroma 集合并用新模型全量重编码所有块;
  3. 重建期间检索服务降级(提示"索引重建中")或走旧集合,重建完成再切换读路径(蓝绿切换,避免长时间不可用)。
- 检索器/重排器在**每次启动或收到切换信号时,从注册表读取 active 模型路径再加载**,而非写死默认模型。

## 4. 关键设计决策

| 决策 | 选择 | 理由 | 权衡 |
|------|------|------|------|
| 向量库 | **Chroma 容器** | 轻量、持久化、docker 易部署 | 大规模(百万级)需换 Milvus,一期可接受 |
| 混合检索 | bge-m3 稠密 + BM25 | 语义+关键词互补,补专有名词盲区 | BM25 用 2-gram 分词,免 jieba 依赖 |
| 重排 | bge-reranker CrossEncoder | 精度远高于向量粗排,性价比高 | CPU 上对 50 候选打分有延迟,控制 Top-N |
| 稠密/稀疏权重 | 0.7 / 0.3 | 中文制度问答以语义为主 | 需在评估集上调 |
| 生成模型 | 云端 Kimi k3 | 效果好、免本地大模型显存 | 受供应商稳定性/成本影响 → 接口抽象可替换 |
| 抽取与生成分级 | (二期)生成大模型、杂务小模型 | 降本 | 一期统一用 k3 |
| 拒答阈值 | reranker 分数阈值 | 简单有效 | 阈值过严误杀、过松幻觉,必须评估集调校 |
| 模型本地化 | bge 全本地 CPU | 数据不出内网,合规 | CPU 性能有上限 → GPU 升级路径 |
| **模型可注册** | **Model Registry 抽象** | **支持上传自定义嵌入/重排模型,平台化管理** | **切换嵌入模型需全库重建(向量空间改变),需蓝绿切换** |
| **模型加载解耦** | **启动/切换时从注册表读 active 路径** | **不写死模型,支持热切换** | **需维护注册表与生效指针一致性** |

## 5. 性能与容量设计

### 5.1 延迟预算(端到端 P95 ≤ 8s,CPU 底座)

| 环节 | 预算 | 说明 |
|------|------|------|
| 查询理解 | ≤ 0.5s | 一期可省略(直通) |
| bge-m3 编码问题 | ≤ 0.5s | 单句编码快 |
| 混合检索 | ≤ 0.5s | Chroma + BM25 |
| reranker(50 候选) | ≤ 3s | **CPU 瓶颈**,是主要耗时 |
| LLM 生成 | ≤ 3s | 流式降低体感 |

### 5.2 优化杠杆(按性价比)

1. **流式输出(SSE)**:TTFT 决定体感,必做;
2. **reranker 候选数收敛**:Top-N 50→30,延迟近似线性下降;
3. **无依赖环节并行**:稠密检索与 BM25 并行;
4. **缓存**:高频问题的检索结果与答案缓存(注意权限与时效);
5. **GPU 升级**:reranker/编码上 GPU,端到端可压到 ≤ 3s(见路线图)。

### 5.3 容量估算(一期)

- 文档规模:百级制度文档,数千块——Chroma/CPU 完全够用;
- 并发:5~10 并发内部试用,CPU 排队可承受;
- 索引重建:全量重建分钟级(千块级),可接受。

## 6. 安全与权限设计

| 层 | 措施 |
|----|------|
| 数据 | 文档/向量/模型全本地,内网部署;bge 本地推理,不出网 |
| 传输 | 仅脱敏后的查询片段送云端 LLM(prompt 不带无关文档);HTTPS |
| 密钥 | LLM key 存 `.env`,gitignore,不入库不入日志 |
| 权限 | 检索前按用户部门/角色做元数据过滤(`where` 过滤),越权文档不参与召回 |
| 审计 | 提问日志、文档操作日志留痕(脱敏) |

## 7. 可观测性与评估

### 7.1 运行监控四指标(看板化)
- **检索命中率**(召回是否含相关块);
- **拒答率**(突升 = 知识库过期或检索故障信号);
- **端到端延迟 P95**;
- **token 消耗 / 成本**。

### 7.2 质量评估(离线,RAGAS)
- 评估集:50~100 条标注问答(事实/综合/多跳/对抗拒答);
- 检索层:Hit Rate@5、MRR;生成层:Faithfulness、Answer Relevancy;
- 改动单变量回归,杜绝"凭体感调参"。

## 8. 部署架构

### 8.1 一期(单机,内部试用)

```text
┌────────────────────────────────────┐
│  一台服务器(或开发者机器)            │
│  ├─ Docker:Chroma 容器             │
│  ├─ conda env rag:                 │
│  │   ├─ API 服务(FastAPI)          │
│  │   ├─ RAG 引擎(bge 模型 CPU)     │
│  │   └─ SQLite 业务库              │
│  └─ Web 前端(静态/Nginx)           │
└──────────────┬─────────────────────┘
               │ HTTPS(脱敏查询)
               ▼
        云端 LLM(Kimi k3)
```

- bge 推理上 GPU 节点;Chroma → Milvus 集群;SQLite → Postgres;
- 服务无状态化 → 多副本 + 负载均衡;引入查询路由做传统 RAG / GraphRAG 分层。

## 9. 技术选型汇总

| 模块 | 选型 | 备注 |
|------|------|------|
| Embedding | bge-m3(sentence-transformers),**可注册替换** | 默认 1024 维,维度从 config 读取不写死 |
| 稀疏检索 | BM25(rank_bm25,2-gram) | 免 jieba;与嵌入模型无关,换模型无需重建 BM25 |
| 重排 | bge-reranker-base(CrossEncoder),**可注册替换** | 性价比最高的质量杠杆 |
| 向量库 | Chroma(docker) | localhost:8000 |
| LLM | Kimi k3(OpenAI 兼容) | temperature=1 限制,接口可替换 |
| 后端 | Python 3.12 + FastAPI(产品化新增) | conda env `rag` |
| 前端 | (待定,Vue/React + SSE) | M1 交付 |
| 业务库 | SQLite → Postgres(含**模型注册表**) | 渐进 |
| 部署 | Docker compose + conda | 单机起步 |
