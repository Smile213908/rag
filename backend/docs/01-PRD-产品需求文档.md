## 1. 背景与问题

### 1.1 现状
企业内部沉淀了大量制度、规范、流程类文档(如《考勤与假期管理办法》《国内差旅费支出管理办法》),员工查找具体条款时面临:

- **找不到**:文档散落在各处(PDF/共享盘/群文件),不知道去哪查;
- **看不懂**:制度条文冗长严谨,通读成本高,员工只想知道"我这种情况怎么办";
- **问人慢**:依赖 HR / 行政部门答疑,重复性问题占用大量人力,且口径不一。

### 1.2 痛点本质
知识**存在**但**获取成本过高**。传统关键词搜索无法理解自然语言提问(如"我出差住亲戚家能报销吗"),员工需要的不是"返回一堆文档",而是**一个准确、可溯源的直接答案**。

### 1.3 为什么是现在
大语言模型(LLM)+ 检索增强生成(RAG)技术已成熟到可以低成本解决"基于私有文档的自然语言问答"。我们已验证技术底座可行(见 §10 附录:技术验证结论)。

## 2. 产品愿景与目标

### 2.1 一句话定位
> 让员工用**自然语言**直接询问公司制度,获得**准确、带出处、可追溯**的答案——把"查文档"变成"问同事"。

### 2.2 产品目标(首版)

| 目标 | 衡量指标 | 目标值 |
|------|----------|--------|
| 答案准确 | 事实型问题 Top-1 答案正确率(人工抽检) | ≥ 90% |
| 可信可溯源 | 答案带来源标注的比例 | 100% |
| 不胡说 | 库外问题拒答率(而非编造) | ≥ 95% |
| 响应体验 | 简单问题端到端延迟(P95) | ≤ 8s(CPU 底座) |
| 减轻人力 | HR/行政重复性答疑量下降 | ≥ 30%(上线后 3 个月) |

### 2.3 非目标(本期不做)

- ❌ 多模态问答(图片/表格深度理解)——二期;
- ❌ 复杂多跳推理 / 全库总结(GraphRAG 能力)——二期演进;
- ❌ 文档的在线编辑、协同创作——只做"问答",不做"知识管理";
- ❌ 面向 C 端的开放问答——仅企业内部私有知识。

## 3. 目标用户与场景

### 3.1 用户画像

| 角色 | 占比(预估) | 核心诉求 |
|------|------------|----------|
| **普通员工**(查询者) | ~90% | 快速搞清"我这种情况符合哪条规定、怎么办",要准、要快、要可信 |
| **HR / 行政**(知识维护者) | ~8% | 上传/更新制度文档,查看哪些问题被高频询问(发现制度盲区),减少重复答疑 |
| **管理员**(运营者) | ~2% | 管理文档库、用户权限、查看系统健康度与回答质量 |

### 3.2 核心使用场景(用户故事)

**场景 1:制度条款速查**(高频)
> 作为员工,我想直接问"春节放几天假?"、"出差住亲戚家能报销住宿吗",系统给我准确答案并附上制度出处,我能点进去看原文。

**场景 2:跨制度综合咨询**(中频)
> 作为员工,我的问题涉及多个制度("请假超过 3 天要走什么流程,会影响考勤吗"),系统能综合多个文档给出结构化答案。

**场景 3:库外问题兜底**(必须)
> 作为员工,当我问了一个知识库没有的问题("公司股价多少"),系统明确告诉我"现有资料无法回答",而不是编一个答案骗我。

**场景 4:知识维护**(管理侧)
> 作为 HR,新制度发布后我上传 PDF,系统自动解析入库即可被查询;旧制度更新后,答案口径同步更新。

**场景 5:质量运营**(管理侧)
> 作为管理员,我能看到哪些问题被问得最多、哪些答得不好(用户点了踩),据此补充制度或优化知识库。

## 4. 功能需求

### 4.1 功能总览(MoSCoW 优先级)

| 模块 | 功能 | 优先级 |
|------|------|--------|
| 问答 | 自然语言提问、流式输出答案 | **Must** |
| 问答 | 答案标注引用来源,可跳转/展开原文 | **Must** |
| 问答 | 库外问题拒答 | **Must** |
| 问答 | 多轮对话(指代消解) | **Should** |
| 问答 | 答案反馈(👍/👎) | **Must** |
| 知识库 | 上传文档(PDF/Word/Markdown/TXT)自动解析入库 | **Must** |
| 知识库 | 文档列表管理、删除、重建索引 | **Must** |
| 知识库 | 文档更新后增量重建 | **Should** |
| **模型管理** | **上传自定义模型(嵌入/重排),平台解析保存** | **Must** |
| **模型管理** | **模型列表、启用/切换、删除** | **Must** |
| **模型管理** | **切换嵌入模型后触发全库重建** | **Should** |
| 运营 | 提问日志、高频问题统计 | **Should** |
| 运营 | bad case(👎)回流与标注 | **Should** |
| 权限 | 用户登录、按部门/角色控制文档可见范围 | **Could** |
| 权限 | 管理后台 | **Could** |

### 4.2 核心功能详述

#### F1 智能问答(核心)
- **输入**:自然语言问题(中文为主)。
- **处理**:混合检索(稠密语义 + BM25 关键词)→ 重排序 → LLM 基于检索结果生成。
- **输出要求**:
  - 答案**分点、结构化**,关键论断标注 `[来源N]`;
  - 每个来源可展开查看原文片段及其所在文档;
  - **检索结果置信度低于阈值时,直接拒答**(见 F3),绝不硬编;
  - 流式输出(SSE),降低体感延迟。

#### F2 引用溯源
- 答案中的每个 `[来源N]` 对应一个检索片段,展示:文档名、片段内容、相关性分数;
- 支持点击定位到原始文档(一期可定位到文档级,二期定位到段落/页)。

#### F3 拒答机制(信任基石)
- 当重排序最高分低于阈值(阈值需在评估集上调校),判定"库中无答案";
- 返回标准拒答话术 + 建议("换个问法 / 联系 HR"),**不允许模型在弱相关资料上强行作答**;
- 拒答问题进入日志,供运营分析是否为知识盲区。

#### F4 多轮对话(Should)
- 支持上下文指代消解:"那它的价格呢?"→ 结合历史改写为完整问题再检索;
- 会话级上下文管理,可"开启新话题"清空上下文。

#### F5 反馈闭环
- 每条答案旁提供 👍/👎;
- 👎 样本自动进入 bad case 池,附用户可选填的"哪里错了"(没查到/答错了/引用错/拒答不当);
- bad case 驱动知识库补全与检索/生成参数调优(见 [[02-架构设计文档]] 评估闭环)。

#### F6 知识库管理(管理侧)
- 上传文档 → 自动解析(清洗页眉页脚)→ 分块 → 向量化入库,全程无需人工干预;
- 文档列表:名称、上传时间、块数、状态(索引中/已完成/失败);
- 删除文档:级联删除其所有块与向量;
- 文档更新:支持整篇替换重建(一期),二期做增量更新。

#### F7 模型管理(管理侧,核心新增)
> 把模型从「代码写死」变为「平台可管理的资产」,支持用户上传自定义模型并在检索/重排链路中使用。

- **上传**:支持打包上传(zip/tar.gz)的 **HuggingFace / sentence-transformers 标准格式**模型目录(含 `config.json`、权重文件 `pytorch_model.bin`/`model.safetensors`、分词器 `tokenizer.json` 等);
- **模型类型**:分**嵌入模型(Embedding)**与**重排模型(Reranker)**两类,上传时声明,平台据此选用加载器(嵌入→`SentenceTransformer`,重排→`CrossEncoder`);
- **解析与校验**:平台解包后**校验必需文件是否齐全、格式是否可被加载器识别**,并读取 `config.json` 提取元数据(向量维度、最大序列长度、模型结构等)——**校验不通过则拒绝注册并提示原因**,避免坏模型进入链路;
- **保存**:校验通过的模型保存到平台模型仓库(`model/` 目录),写入**模型注册表**(名称/类型/版本/路径/维度/上传人/时间/状态);
- **启用与切换**:平台维护「当前生效的嵌入模型 + 重排模型」,可在已注册模型间切换;切换后检索/重排链路**热加载新模型**;
- **一致性保护(关键)**:**切换嵌入模型 = 换了向量空间**,已有向量失效,平台必须提示并触发**全库重建索引**(重排模型不涉及向量空间,可直接切换);
- **删除**:仅允许删除「未启用」的模型,删除时清理文件与注册表记录;当前生效模型不可删。

**模型管理用户故事**
> 作为管理员,我上传一个领域微调过的嵌入模型 zip,平台校验通过并显示其向量维度;我把它设为当前嵌入模型,平台提示「需重建索引」,确认后全库文档用新模型重新向量化,后续问答即走新模型。

### 4.3 边界与异常处理

| 异常场景 | 处理策略 |
|----------|----------|
| 文档解析失败(扫描件/损坏) | 标记"解析失败",提示人工处理或走 OCR(二期),不阻塞其他文档 |
| 云端 LLM 服务不可用 | 返回"服务暂时不可用,请稍后重试",检索结果可降级直接展示片段 |
| 问题为空/过长 | 前端校验,超长截断并提示 |
| 并发查询高 | CPU 底座下限制并发,排队 + 明确等待提示 |
| 敏感/越权文档 | 按权限过滤后再检索(权限生效在检索前) |

## 5. 非功能需求

| 类别 | 需求 |
|------|------|
| **性能** | 端到端延迟 P95 ≤ 8s(CPU 底座);检索+重排 ≤ 3s;GPU 升级后目标 ≤ 3s |
| **并发** | 一期支持 5~10 并发(内部小团队试用);规模化需 GPU + 服务化 |
| **成本** | 云端 LLM 按 token 计费,需控制单问成本;抽取/生成模型分级(二期) |
| **安全** | 文档为企业内部数据,**bge 模型本地运行、数据不出内网**;仅脱敏后的查询片段送云端 LLM;`.env` 密钥不入库 |
| **隐私** | 提问日志脱敏存储;文档访问按权限隔离 |
| **可维护性** | 索引持久化(Chroma),重启不重算;模型路径可配置 |
| **可观测性** | 检索命中率、拒答率、延迟、token 消耗四项核心指标可监控 |

## 6. 成功度量(如何知道我们做对了)

### 6.1 北极星指标
> **"员工无需找人、自助解决制度疑问"的占比**(自助问答成功数 / 制度类咨询总量)。

### 6.2 分层指标(对应 RAG 评估体系)

| 层 | 指标 | 工具/方法 |
|----|------|-----------|
| 检索层 | Hit Rate@5、MRR | 离线评估集(50~100 条标注问答) |
| 生成层 | Faithfulness(忠实度)、Answer Relevancy | RAGAS 框架,LLM 当裁判 |
| 体验层 | 👍率、拒答恰当率、P95 延迟 | 线上埋点 |
| 业务层 | HR/行政重复答疑量下降、自助解决占比 | 上线后对比 |

### 6.3 评估闭环(必须建立)
```
离线评估集 → 上线 → 收集 👎/拒答日志 → bad case 聚类归因(检索/生成/知识盲区)
   ↑                                              ↓
   └────────── 优化后回归评估 ←──── 针对性修复 ←──┘
```

## 7. 约束与依赖

| 类型 | 内容 |
|------|------|
| 技术约束 | 当前为**全 CPU** 底座,性能有上限;huggingface.co 被墙,模型走 ModelScope |
| 依赖服务 | 云端 LLM(Kimi k3,注意其 temperature 限制)、Docker(Chroma 容器) |
| 数据依赖 | 需 HR/行政提供**权威、最新**的制度文档源;扫描件需 OCR(二期) |
| 合规约束 | 企业数据不出内网(bge 本地化),送云端的仅脱敏查询片段 |

## 8. 风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| 答案幻觉损害信任 | 高 | 拒答机制 + 强制引用 + 评估集回归;"宁可拒答不可硬编" |
| CPU 性能不足,体验差 | 中 | 一期限定小范围试用;规划 GPU 升级路径(见路线图) |
| 制度文档更新不及时 | 中 | 明确知识维护责任人(HR/行政),文档更新流程化 |
| 云端 LLM 成本/稳定性 | 中 | 用量监控;预留可替换的 OpenAI 兼容接口(已抽象) |
| 复杂问题(多跳/总结)答不好 | 低(一期) | 明确一期边界;二期演进 GraphRAG |

## 10. 附录:技术验证结论(M0 已完成)

传统 RAG 底座已端到端验证(详见 [[02-架构设计文档]]):
- **链路**:PDF 解析清洗 → 结构分块(42 块)→ bge-m3 稠密向量(Chroma 持久化)→ bge-m3 + BM25 混合检索 → bge-reranker 精排 → Kimi 生成;
- **已验证能力**:跨文档准确分流、多片段综合、库外问题诚实拒答、答案带引用溯源;
- **样本表现**:对"出差住宿补贴"等问题,答案准确且能纠正表述细节,忠实度良好。

> 该底座即本 PRD 的 M0 成果,产品化在其上叠加交互层、知识库管理与运营闭环。
